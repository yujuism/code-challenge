# Problem 5: A Crude Server

A CRUD API for a generic "resource", built with Express 5 and TypeScript, with data
stored in SQLite.

## Running it

It uses Node's built-in `node:sqlite` module and runs the TypeScript files directly, so
there's nothing to compile on install. Requires Node.js 22.22+, 24.15+ or 26+ (Node 24 LTS recommended).

```bash
cd src/problem5
npm install
npm run dev                  # development, restarts on file changes
npm run build && npm start   # production build
```

The server runs on `http://localhost:3000`. It can be configured with environment
variables:

| Variable  | Default             | Description                                                    |
| --------- | ------------------- | -------------------------------------------------------------- |
| `PORT`    | `3000`              | Port to listen on                                              |
| `DB_PATH` | `data/resources.db` | SQLite file. It's created on first start, along with the table |

Other commands: `npm test` and `npm run typecheck`.

## Resource fields

| Field         | Type                       | Notes                                         |
| ------------- | -------------------------- | --------------------------------------------- |
| `id`          | string (UUID)              | Generated by the server                       |
| `name`        | string, 1–200 characters   | Required. Spaces at the start and end are removed |
| `description` | string, up to 2000 characters | Defaults to `""`                           |
| `status`      | `"active"` or `"archived"` | Defaults to `"active"`                        |
| `createdAt`   | ISO date string            | Set by the server                             |
| `updatedAt`   | ISO date string            | Set by the server on every update             |

## Endpoints

| Method   | Path             | Success                                  | Errors     |
| -------- | ---------------- | ---------------------------------------- | ---------- |
| `POST`   | `/resources`     | `201` with the new resource              | `400`, `413` |
| `GET`    | `/resources`     | `200` with `{ data, pagination }`        | `400`      |
| `GET`    | `/resources/:id` | `200` with the resource                  | `404`      |
| `PATCH`  | `/resources/:id` | `200` with the updated resource          | `400`, `404` |
| `DELETE` | `/resources/:id` | `204` with no body                       | `404`      |
| `GET`    | `/health`        | `200` with `{ "status": "ok" }`          |            |

`PATCH` only changes the fields that are sent.

### Filters for `GET /resources`

| Parameter | Description                                                        |
| --------- | ------------------------------------------------------------------ |
| `status`  | `active` or `archived`                                             |
| `q`       | Searches `name`, ignoring case. `%` and `_` are treated as normal characters |
| `limit`   | 1–100, default 20                                                  |
| `offset`  | 0 or more, default 0                                               |

Results are sorted newest first. Unknown parameters return `400`, so a typo like
`?stauts=active` gives an error instead of quietly returning everything.

### Examples

```bash
curl -X POST localhost:3000/resources -H 'content-type: application/json' \
  -d '{"name":"Design doc","description":"Q3 roadmap"}'

curl 'localhost:3000/resources?status=active&q=design&limit=10'

curl localhost:3000/resources/<id>

curl -X PATCH localhost:3000/resources/<id> -H 'content-type: application/json' \
  -d '{"status":"archived"}'

curl -X DELETE localhost:3000/resources/<id>
```

### Errors

All errors have the same shape:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Request validation failed",
    "details": [{ "path": "name", "message": "Name is required" }]
  }
}
```

The possible codes are `validation_error`, `invalid_json`, `bad_request`, `not_found` and
`internal_error`. Unexpected errors are logged on the server, and the client only gets a
generic `500` message.

## Code structure

```
src/
  server.ts                 starts the server and closes the database on shutdown
  app.ts                    Express setup: JSON parsing, routes, error handling
  db.ts                     opens SQLite and creates the table
  errors.ts                 error classes and the error handler
  resources/
    router.ts               HTTP layer: validates input and sends responses
    service.ts              business logic: IDs, timestamps, "not found"
    repository.ts           SQL queries
    schemas.ts              zod schemas and types
test/
  resources.test.ts         API tests over HTTP
  service.test.ts           service tests without HTTP
```

Notes on the implementation:

- Input is validated with zod. Fields that aren't part of the schema (for example `id` or
  `createdAt`) are rejected rather than ignored.
- All SQL uses bound parameters, so user input is never inserted into the query text.
- `PATCH` is a single `UPDATE … RETURNING *` statement, so a partial update can't be
  mixed with another request halfway through.
- Request bodies are limited to 100 kB.
- On `Ctrl+C` or `SIGTERM`, the server finishes the requests in progress and then closes
  the database.

## Tests

`npm test` runs 24 tests against an in-memory SQLite database. The API tests cover
creating, listing, filtering, paging, updating and deleting, along with invalid input,
broken JSON, oversized bodies and unknown IDs. The service tests check ID and timestamp
handling and the "not found" errors directly.

## Not included

- Authentication and authorisation. The brief doesn't mention users. In a real app every
  route would need a logged-in user, and resources would belong to an owner.
- Rate limiting. This is usually done at the gateway, or with `express-rate-limit`.
- Protection against two people editing the same resource at once. The last write wins.
  An `ETag` / `If-Match` check could prevent lost updates.
- Database migrations. The table is created with `CREATE TABLE IF NOT EXISTS`. A real
  project would use versioned migrations.
